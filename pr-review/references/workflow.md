# Review workflow

Maintain a small evidence ledger in context; no persistent agent runtime is required.

0. **Establish boundary.** Identify tools, repository root, dirty work, scope and revisions. Resolve explicitly requested refs; do not substitute a guessed main branch. Enumerate staged/unstaged/untracked files only when included in the requested scope. A supplied diff or immutable before/after snapshots can define scope without Git. Record unknown base/head, partial pagination, binary/generated diffs and unavailable files. If the intended comparison cannot be established, ask the smallest necessary question or review only the explicitly available scope with a limitation.
1. **Gather intent.** Prefer explicit user story/criteria; then authorized ticket/PR context; PR links/description; commits/branch metadata; relevant docs/tests/code. Record objective, expected behavior, constraints, contradictions, provenance and inference confidence. Distinguish no ticket from an inaccessible ticket. Do not choose among ambiguous linked tickets silently. Explicit criteria prevail over inferred intent; contradictions remain visible.
2. **Map requirements.** Split compound criteria into observable behaviors. Keep stable IDs and map each to implementation, meaningful tests, boundary/failure paths, assumptions and one coverage state. Follow requirements-traceability.md.
3. **Locate architecture.** Read relevant entrypoints, package boundaries, models, dependencies, callers/consumers, events, persistence and deployment config. Describe evidenced patterns, not an imagined architecture. Expand only for changed contracts or concrete risks.
4. **Inspect the change.** Account for added, modified, deleted, renamed, generated and config files. Relate behavior to criteria; inspect success/error/retry/input paths and unchanged consumers. Check omitted support work, compatibility, unrelated scope and test realism. Record reviewed versus known total changed-file counts; unknown totals are null, not zero.
5. **Run risk passes.** Consider all twelve dimensions, deepening those triggered by auth, data, API, concurrency, UI/accessibility, dependency/build or similar concrete changes. Bound exploration to the requested mode and observed risks.
6. **Verify candidates.** Re-read source and trace a reproducible scenario; search callers, guards, invariants and counterevidence. Where permitted, use focused safe validation. Establish before/after attribution, impact and confidence; deduplicate by root cause/scenario. Move unresolved hypotheses to residual risks, not confirmed findings. Do not invent locations or execution results.
7. **Separate completeness audit.** After the first investigation, reconcile all criteria and changed areas against the ledger. Check omitted state transitions, negative paths, migrations/config/docs/exports, realistic production-path tests, downstream compatibility and pre-existing attribution. Reconcile validation claims with actual evidence. This is a distinct pass, not a rename of step 4.
8. **Report.** Apply severity calibration and the report contract. Reconcile IDs/counts, requirement links, scope, known lines and blocker rationale. Report limitations even when risk is established. Stop: scoped investigation plus candidate verification plus completeness audit is enough; lack of findings is not a reason to search forever.
